# AGENTS.md

A DeepSeek Harness (DSH) plugin that searches and installs plugins from the `awesome-dsh-plugin` curated registry. TypeScript, ESM.

## Commands

- `pnpm install`
- `pnpm build` — the only build step: `tsc` compiles `src/` → `lib/`, then `scripts/build-client.mjs` bundles `client/` → `lib/client.js`. No test, lint, or typecheck scripts exist.

## Architecture

- `src/*.ts` is source; `lib/*.js` is **generated by `tsc` but committed** and is the package `main`. Never edit `lib/` directly — edit `src/` then run `pnpm build`.
- Module system is ESM + `moduleResolution: NodeNext`, so relative imports **must use the `.js` extension** (e.g. `import { loadRegistry } from './registry.js'`).
- `src/index.ts` — the plugin `apply(ctx)`; registers two DSH tools (`search_dsh_plugins`, `install_dsh_plugin`) and wires the web-only HTTP routes via `ctx.inject(['webServer'], …)`.
- `src/registry.ts` — fetches/caches the remote `plugins.json` (1h TTL, 4s timeout), falls back to `data/registry-snapshot.json`; search/rank and install-spec logic.
- `src/install.ts` — installs into the current profile's `cordis.patch.yml`: profile discovery, `corepack pnpm add`, patch append (serialized via a write queue).
- `src/server.ts` — registers `GET /api/dsh-plugin-registry/search` and `POST /api/dsh-plugin-registry/install` on `ctx.webServer`, reusing `registry.ts`/`install.ts`.
- `client/client.tsx` — the browser bundle source (React settings page, `settings.section` slot). Built by esbuild, **not** `tsc`; no type-check (esbuild only). `react`/`react/jsx-runtime` are externals provided by the DSH web shell.
- `data/registry-snapshot.json` — bundled offline fallback (275 plugins). Refresh it from the remote URL in `src/registry.ts` if it goes stale.

## Gotchas

- Peer deps `@deepseek-ai/cordis` and `@deepseek-ai/dsh-tools` are internal scoped packages; don't add them as regular deps.
- `install.ts` has a Windows-specific `pnpm` exec path (runs `corepack.js` via `node` because `.cmd` shims can't be `execFile`'d); keep it when touching the install flow.
- The `dsh` CLI is not a local dependency (`.bin` only has `tsc`/`cordis`); dev loading uses `dsh plugin --profile web add .` then `dsh web`.
- `dev.cordis.patch.yml` is gitignored (dev-mode patch); `cordis.patch.yml` is the committed bundle patch that enables this plugin itself.
- In a `--patch` overlay, a relative entry `name` resolves against the **profile directory** (`$DSH_HOME/profiles/<name>`), not the patch file or cwd. Crucially, `--patch` (even an absolute `file:///` URL) only loads the **host** side — the web UI client bundle is discovered by `dsh-client-modules` resolving the entry's package **by name** (`require.resolve(name + '/package.json')`), so it must be installed by name. Dev the UI with `pnpm build && dsh plugin --profile web add . && dsh web`.
- The web UI requires the `dsh.client` manifest + `exports["./client"]` in `package.json`; the bundle must register itself via `window.__ModuleLoader__.load({ id: <package name>, factory })`. `scripts/build-client.mjs` emits this wrapper with esbuild — don't hand-edit `lib/client.js`.
- `src/server.ts` routes register under `ctx.inject(['webServer'], …)` so headless profiles (no `webServer`) still work; the sub-fiber just stays PENDING.
- `pnpm-workspace.yaml` sets `allowBuilds: { esbuild: true }` — required under pnpm 11 or esbuild's postinstall is skipped and `pnpm build` fails its deps check.
